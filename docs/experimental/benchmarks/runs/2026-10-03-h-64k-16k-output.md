# H at 64 Ki context with a 16 Ki output ceiling — 2026-10-03

This repeats the [50K/8192 tests](2026-10-03-h-8k-output.md) using the same
model with explicit `num_ctx=65536`, `num_predict=16384` overrides. Saved
model settings and production defaults are unchanged.

Later [fresh boundary probes](2026-10-03-context-ceiling.md) passed 65536
on 4/4 GPU-only loads. The offloaded workload below remains valid; placement
varies with resource conditions. The later short probes do not replace these
workload timings or establish full-context reliability.

## Protocol and placement

- Same H weights, template and saved sampling; thinking off.
- Empty daemon before clean preload; q4_0 KV cache, Flash Attention and one
  inference slot verified from the effective service environment.
- Preload reports **15% CPU / 85% GPU** at 65536 context. The 50K run was
  entirely on GPU. CPU offload is retained and measured in this test rather
  than excluded; it reproduces the earlier clean 64 Ki placement result.
- Three sequential warmed repetitions of the same four-question scout
  fixture, the same 30000-character summary through `summarize_output`, and
  the same historical 36-record direct `/api/generate` inventory request.
- Scout/summary HTTP deadline: 120 seconds per call. Inventory deadline:
  600 seconds. No timeout reruns. Preloading is excluded from task timings.
- Prompt reuse affects timings. Context and output ceiling both changed;
  this comparison cannot isolate their individual effects or establish a
  speed difference from repeated paired trials.
- Raw settings, requests, outputs, metrics, SHA, placement and GPU samples:
  ignored `benchmark-data/qwen-context/h-64k-16k-2026-10-03/`. One detached
  locked supervisor ran the sequential tests.

## Long inventory and decision

- Actual input: 13520 tokens; output: 13446 tokens; natural `stop`.
- End-to-end: 435.572 seconds (7.26 minutes), within the 600-second deadline.
  Prompt evaluation: 69.805 seconds; generation: 365.535 seconds,
  about 36.8 output tokens/second.
- Valid JSON with all 36 records and IDs in order. All file/line locations
  match. 35 records match verbatim; record 21 replaces an em dash in source
  text with a literal `\u2014` escape. Full transcription fidelity fails.
- The 50K/8192 run stopped at its ceiling after 258.792 seconds with
  incomplete JSON. Comparing those totals does not measure a slowdown for
  equivalent completed work: the new run generated 5254 additional tokens.
- Historical A/32K with 16384 took 353.1 seconds and produced 13443 tokens,
  with 29/36 exact records. That separate run is context, not a controlled
  placement-speed or quality comparison. No 50K/16384 paired run was done.

All 67 sampled placement snapshots retained context 65536 and a model
VRAM/total-size ratio of 0.8453, consistent with the preload's 15% CPU /
85% GPU report. Peak sampled device usage: 5017 MiB across 335 samples.
Sampling was approximately every two seconds for device memory and every
ten seconds for placement; host RAM and between-sample peaks were not measured.

The 65536/16384 combination runs these workloads without timeout and completes
the long output that 8192 truncated. It is usable with mixed CPU/GPU placement,
but is not a GPU-only replacement for 50K and does not eliminate fidelity or
selection errors. These inputs reach only 13520 actual tokens; they do not
establish reliability near the full 64 Ki window or prove 64 Ki is required
for the long answer.

Recommendation: retain 50K as the GPU-only operational default; use 16384
explicitly for longer output, and 65536/16384 for larger inputs when mixed
placement is acceptable. Before choosing 64 Ki as a universal default,
compare 50K/16384 on the same completed workload and test representative
larger input with deadlines and fidelity scoring. Tightening the overly
conservative byte check may also avoid some need for a larger context.
No saved model settings or production defaults were changed by this test.
